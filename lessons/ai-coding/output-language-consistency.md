## 现象

同一条回复或同一份文档里语言风格来回漂移，典型形态：

- 中文句子里夹英文单词：「已 pass 三查」「本次 fail 的原因是……」。
- 英文标签直接嵌进中文句子：「BEFORE/LOGCAT_TOTAL_LINES 等标签夹在中文句中」。
- 文档正文、代码注释、任务清单各自使用不同语言，同一文件内前后不一致。

## 根因

只有「跟随用户语言」这类泛化要求，没有「哪类内容用哪种语言」的判定规则。每次输出靠临场习惯，风格随命令、段落、上下文切换而漂移；同一会话里越往后越容易失守。

这不是模型能力问题，是缺少可执行的约束。

## 处置

把判定口径写成两类清单，而不是「尽量统一」：

1. **面向人的文字 → 中文**：回复、文档正文、说明与结论、任务清单与 Todo、表格表头与说明列。
2. **技术标识 → 原样保留英文**：命令、路径、包名、环境变量、代码标识符、工具原始输出。
3. 引用原始日志或报错栈时，保留英文原文，紧随中文解释，不翻译报错。
4. **MUST NOT**：整段英文；中文句夹英文单词。`pass` / `fail` 一律写「通过 / 不通过」。

落点为项目或仓库内的规则文件，与代码同源管理，避免只存在于对话里。

## 证据

- 按该口径重写文档后，抽查连续 10 段正文，无「中文句夹英文单词」形态。
- 规则写入规则文件后可被 review 引用；后续条目与手册全文按同一口径撰写。
- 反例保留：修复前的原文即为「已 pass 三查」，可直接对照。

## 教训

- 语言一致性靠规则，不靠「注意一点」。有清单就能 review，没有清单只能靠感觉。
- 先定「人读 / 机读」两类，再谈细节；顺序反了会陷入逐词争论。
- 保留原始报错英文是硬要求：翻译过的报错无法用于检索和复现。

## 适用边界

- 适用：面向中文读者的 Agent 回复、项目文档、经验条目、任务清单。
- 不适用：代码本体、提交信息、面向英文团队的对外沟通、必须逐字保留的上游文档引用。
